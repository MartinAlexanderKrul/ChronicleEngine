## 2026-08-14 — The line-ending policy had argued its own case for months and had no enforcer

**Engine tooling; refinement under Decision 069, owned by Version 0.4.** No Rules, Data Model, or Runtime mechanism change. The classification argument, stated rather than pronounced: this touches no section of `010_ENGINE_RULES.md` and does not change `011_ENGINE_DATA_MODEL.md` at all; on the third leg, a gate that enforces a policy `.gitattributes` already declares falls inside Decision 069's carve-out for a change that *"only sites, enforces, or makes explicit an obligation the engine already carries."* Nothing here creates an obligation — `* text=auto eol=lf` has been the rule all along.

**Problem: the policy was written, argued at length, and never checked.** `.gitattributes` records two prior false readings in its own comment — *"a concealed-record count that read 0 against a CRLF ledger while the identical pattern read 5 against an LF one"*, and a `test_progression_audit_contract` diagnosis *"sent down two blind alleys because `git checkout` and `git worktree` silently rewrote endings."* It then reasons carefully about why checkpoints take no exception. **All of that was prose.** No gate read it, and `git` cannot be the enforcer here: `text=auto` normalises on compare, so a working file that is CRLF on disk while the index holds LF is reported **clean** by `git status`. Git is satisfied; every tool in `tools/` reads raw bytes and is not.

It recurred on 2026-08-14. A play session left `160_CAMPAIGN_CHRONICLE.md` CRLF in the working tree, and `^kind:[ \t]*combat[ \t]*$` **matched 0 events instead of 36** — `$` in .NET multiline mode matches before the `\n`, and the `\r` sits in the way. `validate_repository.ps1`'s boss-kill rule skipped every Event in the campaign and validation **reported PASSED**: not because the records were sound, but because the check was not running.

**That is what distinguishes this from an ordinary stale value, and why it earns a gate rather than a note.** A stale constant fails one assertion. A CRLF file silently disables every multi-line anchor reading it, so *a green suite underneath one proves nothing* and the failure surfaces somewhere unrelated to its cause. It is the same shape as F-002 and F-013 pointed at the test harness itself.

**Measured, not assumed: 670 tracked files were in violation** — 585 `crlf` and **85 `mixed`**, the latter worse, since a pattern can match some records in a file and silently skip others. **Zero were wrong in the index.** The committed canon was correct throughout and only the checkouts were wrong, which is precisely what `.gitattributes` predicted; normalising the working tree left the index byte-identical, and `git diff` reports **zero content differences under `saves/`**. Checkpoint immutability is untouched, and the file's measured claim is now confirmed a second time rather than trusted.

**A second defect fell out of the same sweep: 271 of the 670 were a test fixture that had been committed.** `tmp/progression-audit-6c5c3685…` holds 669 files and 50 MB captured at `8dfe8f4`, including a 155 KB copy of the character sheet frozen at that date. `test_progression_audit_contract.ps1`'s own comment already indicts it — *"A test fixture has no business being reachable by a commit at all"* — and the tool was fixed to write to the system temp directory, but **the leftover outlived the fix**. A stale duplicate of live campaign state sitting inside the tree is F-018's defect exactly. Untracked and added to `.gitignore` with the reason; the files remain on disk.

**Change:** new `tools/test_line_endings.ps1`. Two things are deliberately not restated in it. The **policy** is parsed from `.gitattributes` — a gate carrying its own copy of a rule owned elsewhere is F-013's defect, met three times now on a ladder ceiling, a budget literal and a fixture. Which files are **text** is likewise git's answer and not the gate's: `git ls-files --eol` yields git's own per-path reading of the attributes, including `-text` for the declared PDFs and for anything it detects as binary. An extension allowlist maintained in the gate would be the same duplication one level down and would silently stop covering any new file type. Tracked paths are checked through that inventory; untracked-but-not-ignored paths are byte-scanned, because a file just written and not yet added is exactly how this arrives, and `--exclude-standard` keeps scratch out on git's judgement rather than a pattern list. The gate refuses to pass on an enumeration under 100 files — reproducing the vacuous pass it exists to catch would be a poor joke.

**Files:** `tools/test_line_endings.ps1` (new), `.gitignore`, `engine/030_ENGINE_CHANGELOG.md`, and 356 working-tree files normalised to LF with no index or content change.

**Audit:** eight legs verified by mutation, each restored afterward — a clean tree passes; one untracked CRLF file fails; mixed endings fail; a NUL-bearing file carrying CRLF passes; a clean LF file passes; a deleted `eol=` policy fails rather than passing vacuously; a policy flipped to `eol=crlf` fails rather than being silently accepted. **The mutation run earned its keep by finding a real defect in the gate:** with exactly one offender, the filtered collection collapsed to a bare object and `.Count` on it is a StrictMode error, so the gate **crashed precisely in the single-newly-broken-file case it exists to report**, and only the multi-offender path had ever been exercised. Every filtered collection is now `@()`-wrapped. Full suite 37 of 37.

## 2026-08-02 — A Hidden quest's reward is checked where saves are actually gated

**Engine tooling; refinement under Decision 069 (no Rules, Data Model, or Runtime mechanism a world must satisfy).** No ADR, no owner ruling: this enforces an existing world rule, it does not author one.
**Problem:** Gatefall Section 8.4.5 states that a concealed-discovery record **never stores a reward** — Section 8.4.3 fixes it from the Bearer's System Rank at attachment — and `ENT-000190` was found carrying `reward_rank_at_attachment: D-Rank` anyway, inside a promoted checkpoint. The rule was real and written down; the only thing checking it was `test_gatefall_quest_contract.ps1`, **which is not one of the checkpoint's gates**. `new_checkpoint.ps1` runs repository validation, runtime-configuration validation, and the checkpoint contract — so a record could violate a stated rule and the save would still go green. The stored value was also *correct* (D-Rank, and it attached at D-Rank), which is what let it sit unnoticed: a wrong number is caught on first reading, a right number in an unmaintained place is not. The converse was worse and was checked nowhere at all — nothing verified that an attached Hidden quest carries a reward, or that `reward_xp: 150` is the right figure for `reward_rank: D-Rank`. Each field was individually well-formed, which is the same shape as F-011 and the same shape as the duplicate itself.
**Change:** both halves move into `validate_repository.ps1`, which gates every save. A concealed-discovery record may carry no `reward*` key; an **attached** Hidden quest must carry `reward_rank` and `reward_xp`, and the XP must be that Rank's Gate-clear milestone. **Both facts are read out of the governing world's own profile rather than restated in the validator** — the prohibition by the presence of its sentence, the ladder by parsing `E-Rank 70, D-Rank 150, …` from Section 8.4.3 itself. A hardcoded ladder would have become a second copy of exactly the derived value the rule exists to keep in one place, and would drift the first time a world repriced a Rank. A world whose profile does not state these sentences is simply not governed by the check, so this adds no obligation to `reikon` or to any world authored later.
**Files:** `tools/validate_repository.ps1`, `tools/test_validate_repository.ps1`.
**Audit:** four legs, asserted against an **isolated copy of the real repository and the real validator** rather than a self-agreeing fixture — a stored reward on `ENT-000190`, a `reward_xp` of 999 against D-Rank, and a removed `reward_rank`, each required to fail and to name both the offending value and the profile it was judged against. The 999 leg asserts the message contains the derived `150`, which is what proves the ladder was parsed rather than assumed. A fourth leg requires the checks **not** to fire on the live repository, since an unconditional failure would satisfy the first three and block every real save. The suite was run against the gate disabled and failed on leg 1 rather than passing quietly.

## 2026-08-02 — The checkpoint helper could not pass its own gate

**Engine tooling; refinement under Decision 069 (no Rules, Data Model, or Runtime mechanism a world must satisfy).** No ADR, no owner ruling: nothing here changes an accepted decision or the entity schema. Actions F-010.
**Problem:** `tools/new_checkpoint.py` failed three consecutive live invocations at its post-promotion `validate_repository.ps1` gate, on `Generated validation evidence block is not synchronized`, while a standalone run of the same validator against the same live state passed. The evidence block's checkpoint count is derived from the campaign's own save manifests, so `os.replace(staging, final)` staleness-marks it in the instant it makes the checkpoint real — and the helper regenerated the runtime index at exactly that point, twice, generate then `-Check`, while having no corresponding call for the evidence generator anywhere in its sequence. **The helper could never pass its own gate** on any repository where the evidence generator was present. F-010's originally recorded mechanism — a staging directory polluting the generator's `saves/` glob — is superseded: preflight runs before that directory exists and the post-promotion gate runs after it has been renamed away, so **no staging directory exists while either gate runs**. The `.staging-` directories that prompted that reading are created by the rollback path, after the failure rather than before it; they kept their manifests and did break the *next* run's preflight, which is a real second defect and not the first one.
**Change:** a new `evidence-generation` phase between promotion and the post-promotion validation gate, mirroring the runtime-index handling exactly. It is guarded on the generator's presence the same way `validate_repository.ps1` guards its own evidence check, so a repository without the generator is not failed for drifting out of sync with a check nobody runs. The evidence document joins the byte-for-byte rollback set *before* it is written, because a later gate failure would otherwise leave the block advanced past a checkpoint that no longer exists and poison the next preflight — the failure path had the same shape as the success path's bug. `generate_validation_evidence.py` additionally drops dot-prefixed directories from its `saves/` glob, which is not the fix but closes the secondary contamination independently and permanently.
**Files:** `tools/new_checkpoint.py`, `tools/generate_validation_evidence.py`, `tools/test_transactional_checkpoint.ps1`, `tools/test_name_collision_check.ps1`, `engine/004_DESIGN_FLAGS.md` (F-010 → Actioned, F-011 → Open).
**Also fixed, found in the same sweep:** `test_name_collision_check.ps1`'s clean-name control was `Marnie Sokolov`, and the Gatefall campaign authored `ENT-000189` "Marnie" on 2026-08-11 — so the control shared a token with live canon and the leg failed on its own fixture rather than on the checker. **The F-009 shape, landing on the suite built to catch it.** The control is now a name outside any plausible roster, with a comment saying why it has to stay there. `F-011` is raised but deliberately not actioned: a mastery ascension narrated in `EVT-000303`'s promoted description was never written to its counters, and resolving it moves live damage multipliers.

## 2026-07-28 — A quadratic removed from repository validation; micro-optimization exhausted

`Get-LineNumber` resolved a line by taking `Substring(0, index)` and counting newlines in the copy — O(n) per lookup, once per identifier occurrence. The scan performs 5,403 of those across the live set against files up to 259 KB, so the term was quadratic in chronicle size on a gate that runs at every save. It now builds each file's newline offsets once and binary-searches them. Reference line numbers are also resolved lazily: the consumer deduplicates by identifier and reports on a handful, so resolving all 5,403 eagerly produced values almost none of which were read.

Best-of-three, like for like: **3.74 s → 3.14 s, 16% faster.** Correctness is unchanged — the new lookup was checked against the old implementation across every offset of a sample, and the validator's own regression suite passes.

**The remaining cost has no hot spot, and this is the useful result.** Six hypotheses were measured and five refuted: fixture copying (~4 s across the whole suite), process startup (parse 0.015 s, launch 0.179 s), the per-block helper functions (0.09 s + 0.08 s over the real block set), per-block field regexes (0.01 s over 492 blocks), and object-creation volume (0.1 s for 5,403 allocations). Reading every file and extracting all 541 blocks with nine field regexes costs 0.24 s in total. The residual ~3.1 s is distributed interpretation across roughly a thousand lines of PowerShell, not any one operation.

That settles a question the audit left open. Incremental optimization of this scanner has now been tried and does not reach the twenty-second target; the path is porting the collection pass to the structured parser R10 introduced, which already reads all 492 blocks with a real YAML parser in 0.8 s including interpreter startup. Both `validate_repository.ps1`'s scan and `test_all.ps1`'s note record this so the next attempt does not re-derive it.

## 2026-07-14 — Session Export as durable transcript and recovery source; command-table rendering and destructive-command guards

**Decisions:** Added **Decision 061** (Session Export as Durable Transcript and Recovery Source), refining Decision 056. Decision 056 classified `/export` output as "a non-canonical **derived** artifact... like the player briefing and the Progression Surfacing view." That is a category error: the briefing and the progression view are computed from canonical ledgers and can be regenerated, whereas **a transcript cannot be regenerated from canon** — it is the primary record canon was promoted *from* (Decision 042), and once the session ends it is unreproducible. An export is reclassified as a durable **Gameplay Transcript** (the record class Rules Section 2.8 already defines), the durable form of the tier-2 record the canon hierarchy already ranks above ledgers.

**The bright line is unchanged.** An export still establishes no canon, mints no identifiers, runs no barrier, is never a restoration entry point, and `/export` remains distinct from `/save`. Where every checkpoint has failed, ledgers may be rebuilt from an export by **re-promotion** — a repair operation that runs the Promotion Barrier and the Repository Validation Barrier and produces canon the ordinary way. `/load` restores a checkpoint; recovery from an export reconstructs one.

**Sufficiency contract:** an export must now capture, beyond every message verbatim and classified, the **opening state**, every **resolution in full** (natural roll, net modifier steps and the circumstances behind them, effective result, band — per Decisions 052 and 058), every **identifier allocated** with the object it names, every **promotion** with provenance, and the **closing state**. Message text alone shows what was narrated, not the identity graph the session produced. Recovery reuses attested identifiers — the same object restored to the record, not a retired number reissued (Data Model Invariant 3) — and records gaps rather than guessing where the export is silent.

**Runtime Profile (1.25):** Session Export section rewritten (primary-not-derived; The Bright Line; the sufficiency contract; the required structured sections; the Recovery from an Export procedure). `/export` command-table row updated.

**Command-table rendering.** Added "The Command Table Is Rendered, Not Recalled": `/help` renders from the Command Table and is never answered from memory or paraphrase; shortening a row may drop detail but never change meaning. This mirrors the requirement already placed on a world's diegetic render template, applied to the control surface, and its enforcement point is the render itself (Decision 055). The `/restart` and `/load` table rows carry the guards.

**Start Guide (2.10):** `/restart` marked destructive and described in full player-facing terms ("not 'reload my last save' — that's `/continue`"); `/export` described as complete enough to rebuild a campaign from; `/load` notes it refuses non-restorable checkpoints.

## 2026-07-13 — Checkpoint Gate: Reserved-Marker Consumption Advances the High-Water Mark

**Start Guide / Runtime Profile:** Clarified the checkpoint-completeness gate in both resident layers of `docs/GAMEPLAY_START_GUIDE.md` and the Save Algorithm (step 3) of `docs/AI_GAMEPLAY_RUNTIME_PROFILE.md`: registry allocation means **advancing the kind's high-water mark**, not merely mentioning the identifier. Root cause: the engine saw the id already "mentioned" in the registry and concluded no registry work was needed, missing that a reserved marker being consumed requires advancing the high-water mark. The checkpoint-completeness gate fired correctly otherwise — CP3 wrote six ledgers plus a manifest with read-back, a clean pass versus CP2's silent single write.

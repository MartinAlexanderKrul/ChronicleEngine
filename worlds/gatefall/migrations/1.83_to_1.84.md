## What 1.84 changed

**Nothing a Bearer sees changes. The templates stop disagreeing with the render they describe.**

Section 15.1 has said since 1.63 that *"a rendered window always runs its rules to the nominal 78 cells."* It said so in a paragraph that, in the same breath, licensed every template in the profile to write its rules abbreviated:

```text
╔══ ◈  S Y S T E M ══…
╟──  VITALS  ──…──╢
╚══…
```

The stated reason was byte cost, and it was a true reason: a rule's *run* carries no information, and writing 165 of them out in full costs real bytes on every readiness and operation budget that loads Section 15. **The saving was real and the cost was worse.**

## Why an abbreviation was the wrong instrument

**A template that does not show its own geometry cannot be copied, only interpreted.** That is the whole finding. Section 15.1's own framing says a Runtime *"fills the `<…>` slots from canonical state and changes nothing else"* — but a Runtime cannot change nothing else when the thing in front of it is not the thing it is supposed to emit. 136 of this profile's 165 rules were in that position.

The evidence that interpretation was actually failing is in the 29 rules that *were* written out. Two of them had drifted:

| Rule | Section | Wrote | Should have written |
|---|---|---:|---:|
| `╟──  ACTIVE  ──…  9 known  ────╢` | 15.1's own worked example | 77 cells | 78 |
| `╟──  EARNED  ──…  <n> granted  ──╢` | 16.2 | 77 cells | 78 |

Both drifted the same way — trailing their `─` run *past* the status text instead of closing flush on `╢` — and both sat in the profile uncaught. **Nothing caught them because there was nothing to compare them against.** 27 correct rules and 2 wrong ones are indistinguishable when the other 136 are ellipses. A geometry rule stated in prose beside templates that do not obey it is a rule with no reader.

## The rule

> **Every rule is 78 cells, in the template and in the render alike, and a template is copied verbatim.**

A window's top rule, bottom rule and every inner section rule are **the same length as each other**, so a panel's edges and its dividers align on both margins. Section 15.1 now states the three forms exactly:

- **Top rule** — `╔══ ◈ `, the letter-spaced name, ` ══`, then a `═` run to cell 78. Open on the right.
- **Bottom rule** — `╚` then a `═` run to cell 78. Open on the right.
- **Section rule** — `╟──  `, the name, `  `, a `─` run, closed on `╢` at cell 78. A count or status renders `  <status>  ╢` flush against the closing glyph, the run shortening to absorb it.

**And `…` is not a glyph this profile uses.** It appears in no rule, in no row, and in no template. A run that needs completing is written completed.

## What did not change

**No rendered window changes.** A Bearer who ran `/system` under 1.83 and runs it under 1.84 sees the identical panel, because 15.1 already mandated 78-cell rules and a conforming Runtime was already emitting them.

**No mechanic moves.** No number, price, timer, band, Rank, threshold, population, distribution, skill, class, title, quest rule or behavioral-contract clause is touched. No section is added, removed or renumbered.

**Content rows are untouched**, including the 28 rows across the profile that already run past 78 cells. Section 15.1 has always exempted them — *"a rule is the only thing in a panel with a fixed length"* — and this edge does not revisit that.

## Migration procedure

**1. Advance `profile_version` to `"1.84"`.**

**2. Nothing else moves.** No canonical value is recomputed, re-derived, floored, credited or corrected. This edge transforms no stored state beyond the version field, which is why it is classified `compatibility-treatment` rather than `required-migration`.

**3. Re-render on next call, not retroactively.** A window already written into a chronicle, changelog or export is historical text and is not rewritten. Panels render under the current grammar from adoption forward.

Record adoption as a campaign Event at the adopting campaign's current anchor. Immutable Profile 1.83-and-earlier checkpoints remain byte-unchanged and run the compatibility chain through 1.84 at readiness.

---

## What this does not close

**It does not gate rule width.** Nothing in the suite currently asserts that a frame rule in this profile is 78 cells, which is precisely how the two 77-cell rules survived. The check is cheap and obvious and is **not delivered here** — it is recorded as owed in `engine/030_ENGINE_CHANGELOG.md`, so the next reader finds it named rather than discovering the gap the way this edge did.

**It does not touch Reikon.** `worlds/reikon/206_WORLD_RULE_PROFILE.md` uses a different window style, self-consistent at 63 cells with no abbreviation anywhere in it. It has never had this defect and is not conformed to Gatefall's nominal.

**It does not address the 28 over-wide content rows.** They are pre-existing, they are mostly formula blocks in Sections 6.2 and 11.2 rather than windows, and one is a template row in Section 14.5.4 that runs to 86 cells. Whether a content row should be bounded at all is a separate question from whether a rule is, and this edge answers only the second.
